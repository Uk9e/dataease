# 鉴权改造 / 角色管理 / 嵌入功能：开发工作量评估

> 评估对象：本仓库 `dev-v2` 分支（DataEase v2.10.x 开源版，未包含 X-Pack 源码，`de-xpack/` 为空子模块）。
> 单位：人天（1 人 1 天）。前提：1 名后端（Spring Boot）+ 1 名前端（Vue 3），熟悉对应技术栈，但第一次接触 DataEase 代码。
> 本文的工作量是基于代码阅读的估算，没有做原型验证，误差按 ±20% 考虑。
> 分阶段实施和上线计划见 [auth-role-embed-plan.md](./auth-role-embed-plan.md)。

## 1. 需求理解（需要确认）

| 需求 | 本文的理解 |
| --- | --- |
| 修改鉴权，可以快速跳转到此系统 | 用户已登录你们的其他系统，点一个链接就免登录进入 DataEase（单点登录 / 免密跳转），可以直接打开指定仪表板 |
| 增加角色管理 | 多用户 + 角色，按角色控制能看到哪些菜单、能查看/编辑哪些仪表板、数据集、数据源 |
| 内嵌到其他系统 | 把仪表板/大屏/单个图表嵌入到其他系统页面（iframe 或 div），嵌入时不需要再登录 |

## 2. 现状（开源版里有什么、缺什么）

### 2.1 鉴权

- 登录接口是替补实现 `core/core-backend/src/main/java/io/dataease/substitute/permissions/login/SubstituleLoginServer.java`：
  - 只允许 `admin` 一个账号，签发的 token 固定 `uid=1, oid=1`。
  - **密码校验被注释掉了（第 39-41 行），输入任意密码都能以 admin 登录。** 这是安全问题，建议无论是否做新功能都先修复。
  - JWT（HMAC256）没有设置过期时间，`TokenVO` 返回 `exp=0`。
- 请求校验在 `sdk/common/.../auth/filter/TokenFilter.java` 和 `CommunityTokenFilter.java`：
  - `TokenFilter` 只解码 token、不验签；验签在 `CommunityTokenFilter` 中，且只在“未授权许可证”时执行。
  - 已支持 `X-DE-LINK-TOKEN`（分享链接）；`X-EMBEDDED-TOKEN`（嵌入）只定义了常量，后端没有任何校验逻辑。
- 后端没有 `per_user` 的实体/Mapper，没有用户管理；`SubstituteUserServer` 把当前用户写死为 admin。
- 前端登录页的第三方登录（OIDC/CAS/LDAP 等）全部是闭源插件 `XpackComponent`；开源代码里没有 `?token=` / `?ticket=` 自动登录逻辑。

### 2.2 权限 / 角色

- `sdk/api/api-permissions` 里有 `UserApi`、`RoleApi`、`OrgApi`、`AuthApi`、`EmbeddedApi`、`LoginApi` 等接口定义，**开源代码里一个实现都没有**（实现都在 X-Pack 里）。
- 接口上的 `@DePermit` 注解共 **68 处（10 个文件）**，开源版没有任何切面处理它，等于不做权限校验。注解语义需要从用法反推。
- 菜单接口 `MenuManage.query` 返回全部菜单，不按权限过滤。
- 前端已经有按权限展示的基础：
  - 菜单路由由后端菜单生成（`src/router/establish.ts`），后端过滤菜单后前端自动生效；
  - 资源树节点有 `weight` 字段，`weight >= 7` 才显示编辑/管理按钮，`exportPermission(weight)` 控制导出；
  - `v-permission` 指令按菜单权限隐藏按钮。
- 数据库：开源的 Flyway 脚本不创建 `per_*` 表。你导入的库里有 `per_user`(1 行)、`per_role`(3 行) 等表，是原服务器 X-Pack 建的（`license` 表为空，说明没有激活企业版许可证）。这些表结构可以参考复用，但需要自己写迁移脚本。

### 2.3 嵌入

- **前端已有大部分能力：**
  - div/JS 嵌入 SDK：`src/pages/panel/main.ts`（`new DataEaseBi(type, {token, dvId, baseUrl, outerParams, ...}).initialize()`），`npm run build:flush` 生成嵌入加载脚本；
  - 嵌入模式请求自动带 `X-EMBEDDED-TOKEN`、支持 `baseUrl` 跨域前缀；
  - 预览页 `/preview?dvId=` 已在嵌入白名单，已有 postMessage 与宿主页通信。
- **缺的部分：**
  - 后端不校验 `X-EMBEDDED-TOKEN`，`/embedded/initIframe` 在白名单里但没有实现；
  - iframe 初始化逻辑在闭源插件 `/component/embedded-iframe/Entrances` 中；
  - 没有“嵌入应用”管理（AppId/密钥/允许嵌入的域名）。
- 公共分享链接 `/de-link/:uuid` + ticket 已完整可用，但 `XpackShareManage.proxyInfo` 第 249 行在 iframe 中且无许可证时直接拒绝（这是厂商有意设置的商业版边界）。

### M1 快速跳转（单点登录）

**方案 A：签名票据跳转（推荐，要求对方系统后端能配合签名）**

流程：其他系统后端用共享密钥签一个短时效票据（用户名、过期时间、随机数、目标地址）→ 跳转 `https://bi/#/sso?ticket=...&redirect=...` → DataEase 后端验签、防重放、映射/自动创建用户 → 签发 DataEase token → 前端保存 token 并跳转。

| 工作项 | 人天 |
| --- | --- |
| 后端：`/sso/login` 接口、白名单、验签、nonce 防重放（ehcache）、用户映射/自动创建、跳转地址白名单（防开放重定向） | 3 |
| 前端：`/sso` 路由、`permission.ts` 白名单、保存 token、跳转到目标仪表板 | 1.5 |
| 与对方系统联调、对接文档 | 1.5 |

## 4. 汇总

| 组合 | 包含 | 工作量 | 2 人（前后端各 1）工期 |
| --- | --- | --- | --- |
| 精简版 | M0 + M1 方案A + 菜单级角色 + M3 方案A + 公共 | 约 35-40 人天 | 约 4-5 周 |
| **标准版（推荐）** | M0 + M1 方案A + 完整角色（菜单+资源）+ M3 方案B + 公共 | 约 76-85 人天 | 约 8-10 周 |
| 完整版 | 标准版 + 行列数据权限 + M1 换成 OIDC/CAS | 约 95-110 人天 | 约 11-13 周 |

工期 = 人天 ÷ 2 人，再加约 15% 的联调等待和返工。后端工作量比前端多，后端会在关键路径上；如果加 1 名后端，标准版可以缩短到 6-7 周。

建议的开发顺序：先修复密码校验（立即，0.5 天）→ M0 → M1 → M2 → M3。M1 和 M3 都依赖 M0 的用户体系；M3 方案B 的“限制可访问资源”依赖 M2。

## 5. 风险

1. **后续升级冲突**：要改动 `sdk/common` 的过滤器和替补实现，后续合并 DataEase 官方新版本时会有冲突。建议把新代码放到独立包里，尽量通过新增 Bean 的方式接入，少改原文件。
   - 注意：如果新增名为 `loginServer` 的 Bean，`CommunityTokenFilter` 会改走 X-Pack 的取密钥逻辑（调用不存在的 `apisixCacheManage`），需要一起改。
2. **`@DePermit` 语义没有文档**：处理逻辑在闭源包里，只能从 68 处用法反推，资源级权限是估算误差最大的部分。
3. **现有 SQL 依赖企业版表**：`ExtDataVisualizationMapper.xml`、`DataSetAssistantMapper.java` 中有直接查询 `per_user`、`per_busi_resource` 的 SQL，新表结构需要兼容。
4. **许可证**：项目是 GPLv3。内部使用可以自由修改；如果把修改后的系统分发给第三方，需要按 GPL 开放源码。
5. **替代方案**：DataEase 企业版本身就包含用户/角色/组织、OIDC/CAS/LDAP 等登录方式和嵌入式功能。如果预算允许，可以把采购成本和约 80 人天的自研成本对比一下再决定。

## 6. 需要确认的问题（会影响工作量）

1. 你们的其他系统用什么技术？后端能否配合生成签名票据？是否已有统一认证（CAS、OIDC、LDAP、企业微信、钉钉等）？
2. 角色要细到哪一级：只控制菜单，还是到具体仪表板/数据集，还是到行列数据？
3. 嵌入的是整个 DataEase 还是单个仪表板/图表？嵌入时是否要按访问者身份过滤数据？用 iframe 还是 div？
4. 是否需要组织（多租户）？本文按单组织估算，多组织另加 10 人天以上。
5. 是否考虑采购企业版？
